# 0.13.0 candidates

Forward-looking candidates, in the style of `0.10.0-candidates.md`. Each entry is an
inherent issue observed while dogfooding metareview, with the verified root cause and
the default decision to change.

**How this was found.** Dogfooding metareview on the **Keeper MVP** epic — 16 work
units, one modular monolith, every unit independently reviewed and merged — across
~12 h wall clock overnight 2026-09-21/22. The dominant cost was *process*, not code:
four full mutation regenerations at ~2.5–3.5 h each, a midnight `/tmp` purge that
destroyed worktrees, and review gates that returned `NEEDS_REVISION` for context size
while every substantive lens passed with zero findings.

---

## 1. Generated verification harnesses bind evidence to the WHOLE source+test tree, so any edit re-runs every scope

**Status: TODO — highest-value item.**

### Symptom
A one-line fix in one file (or *any* edit to one test file) invalidated **all 18**
mutation reports and forced a full regeneration of every scope. On Keeper this happened
four times in one night; each round was ~2.5–3.5 h (16 focused scopes + 3 full scopes,
each re-executing per-mutant tests against a real PostgreSQL suite). It turns a
five-minute correctness fix into a three-hour wait and actively discourages making the
fix.

### Root cause (verified)
In a project-local harness generated for the epic, `bin/check-keeper-quality.mjs`:
- `sourceDiscoveryManifest()` hashes the **entire** application source tree, and
  `mutationTestTreeManifest()` hashes **all** of `tests/` (`MUTATION_TEST_TREE_PATHS` =
  `tests/unit`, `tests/integration`, `tests/factories`, `tests/harness`, `tests/helpers`,
  `tests/fixtures`).
- Every raw report embeds both manifest digests, and the verifier rejects a mismatch with
  `STALE_MUTATION_REPORT` / `STALE_MUTATION_TESTS`.
- Therefore adding one new file (even in a different unit) changes the global manifest and
  staleness-invalidates every unrelated unit's report.

Metareview's own mutation model does **not** do this: it binds a mutation to an
**anchor pin** in the specific source (`internal/mutation/verify.go`), verified by exact
text identity — a scoped, local binding. The whole-tree coupling is an artifact of a
hand-rolled harness, not a metareview requirement.

### Default decision for 0.13.0
- Publish the **scoped** binding pattern as the blessed one: bind each report to the
  digests of the files it *actually mutated* and the tests Stryker's per-test coverage
  *actually selected*, never a whole-tree manifest.
- Prefer / document metareview's anchor-pin model for project-generated harnesses.
- Ship a scaffold generator (or template) for project verification harnesses so teams do
  not hand-roll a whole-tree-bound one.
- Where whole-tree binding is unavoidable, add **incremental invalidation**: re-run only
  the scopes whose mutated-file set or covering-test set changed.

### Why it matters
This single default turns every incremental fix in a large epic into a multi-hour
regeneration, and was the largest wall-clock cost of the entire night.

## 2. The shard/lens gate blocks on context size but never generates or runs the shard plan

**Status: TODO.**

### Symptom
`review task-done`, `review epic-ready` and `review pr-ready` all returned
`NEEDS_REVISION` **solely** because of `DIFF_TRUNCATED` / `LARGE_DIFF`:

```
shards covered: 0 of 34; no shard review results were ingested;
manifest blockers: missing cross-shard result; missing shard result for shard-01;
missing shard result for shard-01-10; … ;
Review context risk (architecture-reviewer, blocking, high)
```

Meanwhile the substantive lenses all passed: task-done 3/3 PASS with 0 findings;
epic-ready integration/acceptance/intent-preservation PASS; pr-ready
security/code-quality/external PASS. The only blockers were context-size bookkeeping.

### Root cause (verified)
`internal/reviewers/taskdone.go:42` declares
`shardSatisfiableReasons = {"DIFF_TRUNCATED": true, "LARGE_DIFF": true}` — i.e. those
reasons *can* be satisfied by shard results — and
`internal/reviewmanifest/manifest.go:426` raises `missing shard result for shard-<id>`
when none were ingested. But nothing in the review command derives a shard plan or runs
the shards, so on a large diff (raw ~6.8 MB, filtered ~1.4 MB) the reasons are
**unsatisfiable by construction**: the gate blocks and the agent cannot clear it without
hand-authoring 34 shard-result files.

### Default decision for 0.13.0
- Above a diff threshold, **auto-derive and emit the shard plan**, then run and aggregate
  the shards by default (or require only the high-risk shards).
- Make the shard plan a first-class printed artifact (`--shard-plan`) so an agent can
  satisfy the gate mechanically instead of reverse-engineering it.
- Consider capping/streaming the diff so `filtered` bytes stay under the truncation
  threshold, so the common large-diff case does not trip `DIFF_TRUNCATED` at all.

### Why it matters
A gate that is structurally unsatisfiable on large diffs trains agents to ignore the
gate (or to hand-fabricate shard results), which devalues the rest of the review signal.

## 3. A "bounded review bar" is not a first-class mode

**Status: TODO.**

### Symptom
The project explicitly adopted a bounded bar — *blocking = new P1/security/privacy or
evidence-integrity failures only* — but metareview has no way to declare it. So P2 and
context-size blockers still return `NEEDS_REVISION` and accumulate in
`metareview status --json` / `must_clear`, making the branch look unreviewed even when the
bar was satisfied and the residuals were recorded and accepted by the owner.

### Default decision for 0.13.0
- A supported `--bar bounded|strict` (or repo config) that classifies findings by the
  declared bar, keeps the gate honest, and records accepted residuals as accepted rather
  than as unresolved blockers.
- Let `status`/`must_clear` distinguish "blocked under the active bar" from "advisory
  residual recorded".

### Why it matters
Without it, teams either run the strict gate and ignore it, or fight it — both erode trust
in the gate.

## 4. Evidence regeneration must be a fixed point, and must prove it

**Status: TODO.**

### Symptom
`regenerate-keeper-mutation-waivers.mjs --check` failed **deterministically (2/2)** right
after a successful `write`, then passed after two or three more writes. The diff was not
semantic — it was `provenance` array ordering/content that changed between runs before
converging. In the same night an unrelated one-time mismatch in the ledger appeared
immediately after a long sweep.

### Root cause
The regenerator's output is not canonical: derived arrays (e.g. provenance) depend on
iteration/accumulation order, so `write()` is not idempotent and `--check` re-derivation
disagrees with the file just written.

### Default decision for 0.13.0
- Regenerators must emit **canonical, sorted** output.
- The same command must run `write` then `check` and **fail if the result is not a fixed
  point** (write → re-derive → byte-compare), so a non-idempotent generator can never be
  mistaken for an in-sync ledger.
- Treat provenance/ordering as part of the contract and assert it.

### Why it matters
An evidence ledger that is not a fixed point cannot be trusted to certify, and its
failures look identical to real tamper failures.

## 5. Isolated worktrees default to volatile locations (`/tmp`)

**Status: TODO.**

### Symptom
macOS's daily `/tmp` purge at exactly 00:00 deleted a worktree's `.git` pointer **file**
(the worktree root was under `/private/tmp`), which:
- broke the ledger's git-backed proof carry (`fatal: not a git repository`), and
- made every `verify` crash with a Node stack, looking like a code regression.

Recovery required recreating the `.git` file, `git worktree move` to a durable path, and
`git restore .` for 557 deleted tracked files. The same purge also partially deleted
`node_modules` (missing `ajv/dist/2020.js`).

### Default decision for 0.13.0
- Managed/isolated worktrees (`worktree: true` and FSM `--work-dir`) default to a
  **durable** location (`~/.metareview/worktrees/<repo>/…` or a repo-sibling dir), never
  a platform temp dir.
- Refuse (or loudly warn) when a worktree root resolves under `/tmp`, `$TMPDIR`, or
  similar.
- Before any long run, validate the worktree's `.git` link and tracked-file integrity and
  fail fast with a clear message ("worktree .git is missing; the temp dir may have been
  purged") instead of a downstream stack trace.

### Why it matters
A silent environment purge was nearly indistinguishable from an evidence-integrity
regression and cost ~2 h of recovery.

## 6. Failure output ergonomics on large manifests

**Status: TODO (low effort, high payoff).**

### Symptom
A schema failure printed a **single >50 KB line** of concatenated Ajv errors
(`/records/52/details/0 must … ; /records/52/details/1 must … ; …`), and the verify
summary is one line (`WU16 verification: 138 pass, 0 fail, 4 blocked`) with **no**
failing-record detail at all. Diagnosing took longer than fixing.

### Default decision for 0.13.0
- Structured failure output: a JSON report path **plus** a short human summary naming the
  first N failing records and the first violation per record.
- Never emit unbounded single-line error blobs; wrap and group by record id.

## 7. Long gates vs. agent/subagent turnover

**Status: TODO (orchestration).**

### Symptom
A single mutation regeneration outlived several subagent worker windows and three
watcher timeouts; uncommitted work was stranded repeatedly (recovered manually each time).
The environment (provider `UPSTREAM_ERROR`) also killed two delegated implementation runs
mid-flight.

### Default decision for 0.13.0
- Long-running gates **checkpoint**: commit or persist partial reports incrementally, and
  make a re-run resume rather than restart from zero.
- Watchers should survive provider timeouts and re-attach to resumable state, rather than
  each window being an independent, lossy observer.

### Why it matters
Multi-hour gates are exactly the ones that outlive a single agent turn; if they cannot be
resumed, the process cost is paid in full on every interruption.

## 8. Agent/subagent telemetry is written, but partly to volatile paths and with no analysis surface

**Status: TODO.**

### Symptom
Asked whether the subagents doing the work were storing telemetry an analysis agent could
review, the honest answer was "yes, but not usefully": three disjoint locations, one of
them under `$TMPDIR`, no index, and no linkage to metareview's own review runs. During the
Keeper epic the midnight temp purge (item 5) deleted worktrees — the same purge would have
destroyed the workflow telemetry, and had already reduced full workflow records to 20 of
106 directories.

### What exists (verified)
- `<repo>/.pi/subagents/artifacts/<runId>_<agent>_<i>_{input.md,output.md,transcript.jsonl,meta.json}`:
  durable in the repo working dir. `meta.json` carries `runId`, `agent`, `model`,
  `attemptedModels`/`modelAttempts`, `usage{input,output,cacheRead,cacheWrite,cost,turns}`,
  `durationMs`, `toolCount`, `launchContractDigest`, `acceptance` (criteria, evidence,
  `childReport` with `criteriaSatisfied`, `commandsRun`, `validationOutput`,
  `reviewFindings`, `residualRisks`), `effects`, `transcriptPath`, `timestamp`.
  `transcript.jsonl` holds every tool call and result.
- `$TMPDIR/pi-subagents-<uid>/async-subagent-runs/<id>/` — `mission.json`, `status.json`,
  `events.jsonl`, `control/`, output logs. **Volatile.**
- `~/.pi/agent/sessions/*.jsonl` — parent session transcripts.
- Nothing in `docs/metareview/` correlates a review run with the agent runs that produced
  the reviewed work, so cost/outcome attribution is manual.

### Default decision for 0.13.0
- Write workflow/async telemetry to a **durable** default (repo `.pi/` or
  `~/.metareview/telemetry/`), never `$TMPDIR`.
- Emit a **normalized, append-only run index** (JSONL) alongside the per-run files:
  `runId, parentRunId, agent, model, task hash, started/finished, usage, exit, outcome,
  files touched, review finding ids` — so an analysis agent can aggregate cost, retries
  and failure modes without globbing.
- Correlate runs with metareview review runs (link `runId` ↔ `mrv-…` review id) so the
  cost of each gate is attributable.
- Add a retention/redaction policy and gitignore the artifact tree by default.

### Why it matters
Metareview's value proposition is an auditable, evidence-backed process. The telemetry
that would let you *audit the process itself* — where time and tokens went, which gates
thrashed, which agents failed and were retried — is the one thing not durably and
uniformly recorded. A post-hoc analysis agent currently has to reconstruct it by hand.

A frozen snapshot of this epic's telemetry (214 files, run index, schema, gaps) is kept at
`docs/telemetry/2026-09-22-keeper-epic/` as a worked example of
what is recoverable today and what is missing.

## Cross-cutting theme

Items 1–5 are all the same shape: **a correct-but-global invariant** (whole-tree digest,
all-shards-required, strict bar, global ledger, temp-dir default) makes the *honest* path
expensive, so the process selects for ignoring or hand-fabricating evidence. The 0.13.0
opportunity is to make the smallest-correct-scope the default: bind evidence to the scope
that produced it, generate the work the gate demands, allow an explicit bar, prove the
fixed point, and keep the workspace durable.
