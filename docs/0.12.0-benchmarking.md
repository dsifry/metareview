# 0.12.0 — measuring whether any of this works

Everything metareview claims is currently supported by one uncontrolled observation: on
2026-08-29 a nine-reviewer adversarial pass over 0.9.0's own additions found 72 findings that
every shipped gate had waved through. That is evidence the *review* finds things. It is not
evidence that the harness produces better code, and it says nothing about whether the loop
survives a long task whose requirements change underneath it.

0.12.0 is where that gets measured. **It depends on 0.11.0**: the questions below are about
whether the harness *builds* better code, and the thing that builds is the fix phase, which does
not exist yet (`0.11.0-candidates.md`). Benchmarking before it lands would measure
discovery-and-gating and attribute the result to a build loop.

## The two questions, from Dave (2026-08-29)

1. **Does it get stuck?** Where does an unattended run stall, loop, or need a human?
2. **Does it build better, less buggy code?** Not "does the gate pass" — 0.9.0 passed every gate,
   the 100% coverage requirement and the linter while carrying 12 high findings.

## What already exists — reuse it, do not rebuild

`../harnesseval` is a working evaluation lab, not a plan:

- A completed **384/384 (model x framework x effort) matrix** (batch_083, 2026-08-26) reporting
  recall, precision, incremental recall, hallucination rate against **cost** — the
  quality-vs-cost Pareto frontier. It reuses Inspect AI (runner + token accounting), the Martian
  Code Review Bench (real PRs, human-verified golden comments), and the OpenEnv Code Review Arena.
- `FURTHER-RESEARCH.md` §1 — the **SDLC-loop validation**, the lab's own stated centerpiece:
  `structured-mrv` vs `structured-vanilla` vs naive `/goal`, same model across conditions, scored
  against a **UNION bug universe** so no condition is graded on its own findings, with
  per-iteration convergence and bugs-still-present at the end.
- A prototype on branch `sdlc-loop-experiment` (`bin/run_sdlc_loop.py`,
  `harnesseval/sdlc_loop.py`), **built 2026-08-26 and never run at scale**.

**Known gap:** that prototype drives `harnesseval.adapters.metareview_realistic` and never invokes
`metareview fsm`. It predates the FSM by three days, so as written it measures the pre-0.9.0
harness. Porting it is the first task here.

The lab measures a **single PR**. It has no long-horizon axis and no changing requirements, which
is exactly what questions 1 and 2 are about.

## Primary instrument: SlopCodeBench (SCBench)

[SlopCodeBench](https://arxiv.org/abs/2603.24755) is built for the failure mode this project
exists to prevent. An agent starts from an empty workspace and one requirement, implements it,
and then receives further requirements at successive checkpoints — extending code it wrote
earlier, so its own architectural decisions come back to help or hurt it. Evaluation is black-box
against a CLI/API contract, with no prescribed architecture, and it scores **structural erosion,
duplication, dead branches and verbosity** alongside correctness.

Verified against the paper and the [Snorkel leaderboard](https://snorkel.ai/leaderboard/slopcode-bench/)
on 2026-08-29:

| fact | value |
|---|---|
| v1.0 size | 36 problems, 196 checkpoints |
| agents evaluated | 15, open and closed |
| solved end-to-end | **none** |
| best checkpoint pass rate | **14.8%** |
| trajectories with rising structural erosion | **77%** |
| trajectories with rising verbosity | **75.5%** |

A published [Opus 5 run](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/benchmarking-opus-5-on-slop-code-bench.md)
exists, so there is a baseline to measure against rather than one we generate ourselves.

**The hypothesis, stated so it can lose:**

> Baseline structural erosion rises in 77% of trajectories. Running the same model behind
> metareview's loop and deterministic gates lowers that rate, and the token cost of doing so is
> worth naming.

If erosion is unchanged, the gates do not prevent decay and we should say so. That result is more
valuable than a favourable one, because the whole product rests on the opposite assumption.

The metric list is not incidental: "structural erosion, duplication, dead branches, verbosity" is
a close description of the 72 findings cleared on 2026-08-29 — dead exported fields no caller
read, guards that could not fail, comments asserting properties the code had lost.

## Secondary instruments

- [EvoCode-Bench](https://arxiv.org/html/2605.24110v1) — multi-turn iterative interaction in one
  persistent workspace, where later requirements **correct or contradict** earlier ones. Reported
  as 26 stateful projects / 227 rounds; **those figures are unverified here.**
- [SWE-EVO](https://arxiv.org/abs/2512.18470) — 48 long-horizon tasks from release notes,
  averaging 21 files, ~874 tests per instance.
- [SWE-bench Pro](https://arxiv.org/html/2509.16941) — long-horizon, multi-file.

**Not** plain SWE-bench. It scores whether a patch passes hidden tests on a fixed issue in one
shot. metareview does not write the patch; it gates. A better or worse pass rate would say
nothing about whether the gate catches real defects, which is the claim under test.

**"SWE-STEPS" is unverified and may not exist.** It was described (2026-08-29) as 168 tasks / 963
PRs across six repositories with chains of 3-11 dependent changes, contrasting conversational
against PRD-up-front development and finding isolated evaluation overstates success by ~20
percentage points. Two searches with different phrasings returned nothing under that name. Do not
design a suite around it without a primary source.

## Metrics, chosen so a passing gate cannot be mistaken for working code

**Getting stuck (question 1)** — instrument the FSM, which already records all of it:

- states entered per checkpoint; runs ending `ESCALATED` vs `DONE`
- chain exhaustion (attempt N of max) and forks per lineage
- overrides requested, granted, and — new in 0.11.0-era work — **lapsed**
- host-input requests per task: the count that decides whether "lights out" is real
- wall-clock and tokens per checkpoint, and their trend across checkpoints

Four stall modes are already known from a single day of real use and should be watched for
directly: chain exhaustion after repeated attempts, a dirty-tree blocker that recurred every run,
an override that permanently silenced a check, and an escalation feature that was inert for a
week while reporting success.

**Better code (question 2)** — defect *escape*, never gate pass rate:

- SCBench's own erosion / duplication / dead-branch / verbosity scores, per checkpoint
- checkpoint pass rate against the 14.8% baseline
- **mutation-kill rate on the produced code.** This is the metric today's evidence most supports:
  31 mutations were the only signal that caught defects the coverage gate, the linter and the
  review all passed. Once `mutation-verify` ships in 0.11.0 this is a product feature rather than
  something a human runs by hand, and the eval can read it directly.
- regressions against earlier checkpoints' tests — the "preserve previous behavior" property

## Order of work

1. **0.11.0 first.** Fix phase, `pins`, `mutation-verify`. Without them there is no build loop to
   measure and no in-product mutation signal to read.
2. Port `sdlc-loop-experiment` onto `metareview fsm` so it measures the current harness; run it on
   the single-PR case it was built for. Cheapest real signal, on machinery that already scores.
3. Wire SCBench as a task source and run the erosion hypothesis against the published baseline.
4. Only then consider EvoCode-Bench for the contradicting-requirements axis.

## What would make this eval dishonest

Stated in advance, so the failure is harder to commit later:

- Scoring gate pass rate instead of defect escape. 0.9.0 would have scored perfectly.
- Grading a condition on bugs it found itself. The UNION universe in `FURTHER-RESEARCH.md` §1
  exists for this reason and must be kept.
- Running metareview conditions at higher effort or with more attempts than the controls.
- Reporting N=6-per-cell results as a ranking. The lab's own README already refuses this: Phase C
  (50 PRs + confidence intervals) is the stated bar before any final claim.
- Quoting a benchmark's numbers without checking them. The SCBench figures above were verified
  against the paper on 2026-08-29 and an earlier revision reporting 20 problems / 93 checkpoints
  was found stale; SWE-STEPS could not be verified at all.
