 # Changelog
 
+## 0.14.1 - 2026-10-01
+
+### Fixed
+
+- **The `claude-cli/*` judge runs without the user's hooks, and rejects a turn continued past its
+  verdict.** The codex arm already ran with the user's hooks and plugins off (#193), but the claude
+  arm still loaded the user's settings, so a Stop hook could speak in the judge's session and the
+  recorded verdict could answer the hook instead of the finding. It now passes
+  `--settings '{"disableAllHooks":true}'` (`--bare` would skip the keychain and with it the OAuth
+  session this transport exists to use), and a turn that continues past the verdict is retried and
+  then failed closed — the `--output-format json` envelope exposes only the final result, so the
+  reported turn count (`num_turns`) is the continuation signature. Reported in #193 (bead `mr-bq4`).
+- **Freeform evidence recognizes the tool-failure shapes it was missing.** A text with a success
+  phrase and any failure shape the reader did not enumerate read as *passing* — pytest `no tests ran`
+  (exit 5), `make: *** No rule to make target`, Go `panic:` / `WARNING: DATA RACE`, a shell's
+  `command not found` / `Permission denied` / `Aborted` / `Killed`, `N offenses detected`, and more.
+  The reader now matches a second, **line-anchored** set of shapes: each must start the line in a
+  fixed tool format, with a fixed token before the phrase where the phrase could otherwise appear in
+  prose, so prose that merely names a phrase never reads as a failure. A shape that cannot be pinned
+  that tightly is deliberately not a pattern — prefer an evidence receipt. Tracked as bead `mr-b08`.
+- **`pr-ready` clears a committed review log only when the ledger vouches for every ID under its
+  `## Blocking Findings` section.** The gate used a lenient reading that skipped finding IDs the
+  ledger did not know, so resolving the IDs a local ledger happened to hold retired a log that also
+  listed a blocker nobody's ledger ever held — while `status` still reported it blocking. The gate
+  now uses a strict, blocker-only predicate (an unknown blocking ID is unvouched; the run's
+  `BlockingFindingCount` is the tripwire against a pruned or unknown blocker), and is deliberately
+  **not** strict about the advisory or quoted IDs that would otherwise pin a log unresolved forever.
+  Tracked as bead `mr-ik7`.
+- **The Stop hook breaks its own refusal loop instead of trusting the host's `stop_hook_active`.**
+  Codex reports that flag `false` during hook-driven continuations, so a session blocked on
+  something it could not clear was refused on every turn — a hang, which teaches operators to remove
+  the hook. The hook now counts consecutive refusals per session — a small limit on the *same*
+  blocker set, and a larger session-wide cap for a set that keeps changing — and stands down loudly
+  at either, exactly as the host-driven second pass does, clearing the record on a pass or a
+  stand-down. Its state lives in a private, ownership-checked cache directory and is best-effort: it
+  fails toward blocking, never toward a silent pass. Tracked as bead `mr-j30`.
+
+### Changed
+
+- `.pi/` (pi subagent scratch) is gitignored, and the `.claude/settings.json` review-gate note names
+  the post-#173 user-level hook directory rather than the old per-checkout path.

+    <div class="panel"><span class="tag">Speed</span><h3>Agents write a lot of code, quickly.</h3><p>A coding agent can produce in an hour what used to take a day. Someone still has to check all of it.</p></div>
+    <div class="panel"><span class="tag">False confidence</span><h3>“Tests pass” isn't “it's correct.”</h3><p>An agent (or a tired human) says “done” when the happy path works. The edge case that breaks production isn't tested.</p></div>
+    <div class="panel"><span class="tag">Vague review</span><h3>“Please review this” gets a vague answer.</h3><p>One prompt, no checklist, no record, and no clear rule for when you're actually allowed to move on.</p></div>
+  </div>
+  <p class="bigquote">metareview turns review into a <span style="color:var(--accent)">checkpoint</span>: a set of named reviews, each ending in a clear verdict that tells you what to do next.</p>
+</section>
+
+<section class="slide" data-part="Why">
+  <div class="eyebrow">Part 1 · Why <em>· what it is</em></div>
+  <h2>metareview, in one sentence</h2>
+  <p class="lede" style="font-size:1.35rem;color:var(--ink);max-width:56ch">A command-line tool, plus plugins for your coding agent, that runs <strong>structured, adversarial reviews</strong> at the moments where quality is decided, and <strong>blocks “done”</strong> until real problems are fixed.</p>
+  <div class="grid g3">
+    <div class="plain"><h3>It runs on your machine</h3><p>A local CLI, not a hosted service. Your code isn't sent to a review SaaS. The AI calls go to a model <em>you</em> choose.</p></div>
+    <div class="plain"><h3>It writes its reviews into your repo</h3><p>Every review is a Markdown file under <code>docs/metareview/</code>. You can read it, link to it, and commit it.</p></div>
+    <div class="plain"><h3>It works with your agent</h3><p>Plugins for Claude Code and Codex (and skills for Pi) add slash commands. Or run the CLI directly.</p></div>
+  </div>
+</section>
+
+<section class="slide" data-part="Why">
+  <div class="eyebrow">Part 1 · Why <em>· what it does</em></div>
+  <h2>Four jobs, one tool</h2>
+  <div class="grid g2">
+    <div class="panel"><span class="tag">Main job</span><h3>Review before you move work forward</h3><p>Named review “gates” for plans, small code changes, whole features, and branches. Each one gives a verdict.</p></div>
+    <div class="panel"><span class="tag">Find &amp; fix</span><h3>Find bugs and fix them, with proof</h3><p>A tracked loop (<code>metareview fsm</code>) that finds bugs, confirms them, fixes them, and re-checks. The strictest version requires a test that proves each fix.</p></div>
+    <div class="panel"><span class="tag">Tests</span><h3>Harden tests that only <em>look</em> complete</h3><p>Feed in a mutation-testing report and each mutant that survived becomes a finding: a line your tests run but don't actually check.</p></div>
+    <div class="panel"><span class="tag">Memory</span><h3>Learn from what merged</h3><p>After a PR merges, it pulls lessons into plain files in your repo, so future reviews know this codebase's habits and past mistakes.</p></div>
+  </div>
+  <p class="note">This guide focuses on the first job. It's the one you'll use every day.</p>
+</section>

+<section class="slide" data-part="Why">
+  <div class="eyebrow">Part 1 · Why <em>· what's in it for you</em></div>

+  <div class="grid g2" style="gap:22px 40px">
+    <div class="plain"><h3>You find the bug before your teammate does</h3><p>Problems show up on your machine, before the PR, not as a comment in front of the whole team.</p></div>

+    <div class="plain"><h3>Fewer rounds of PR comments</h3><p>By the time automated PR reviewers and humans look, the obvious problems are already fixed.</p></div>

+<section class="slide" data-part="Why">
+  <div class="eyebrow">Part 1 · Why <em>· the evidence</em></div>
+  <h2>Does a review harness actually find more bugs? It was measured.</h2>
+  <p class="lede">A <strong>harness</strong> runs the model as a team of specialist reviewers working in passes, instead of one prompt over the diff. metareview is a harness. HarnessEval compared the two.</p>
+  <div class="stats">
+    <div class="stat"><b>1.6×</b><span>more verified bugs from the <strong>same model</strong> when it ran in a harness instead of a single prompt</span></div>
+    <div class="stat"><b>39<small>/42</small></b><span>like-for-like comparisons where a harness (metareview or Compound Engineering) beat the one-shot prompt</span></div>
+    <div class="stat"><b>72<small>/147</small></b><span>verified bugs found by open-weight GLM-5.3 running metareview at low effort: <strong>$0.22</strong> and <strong>95 s</strong> a review</span></div>
+    <div class="stat"><b>1/13</b><span>the cost of Opus 5 running metareview, for the same score (0.567)</span></div>
+  </div>
+  <div class="grid g2">
+    <div class="plain"><h3>The trade-off</h3><p>A harness used about 10× the tokens of a single prompt and produced more unsupported findings to check. That's why metareview has a judge that confirms every finding, and a gate that rejects findings pointing at lines you never changed.</p></div>
+    <div class="plain"><h3>Read the fine print</h3><p>Six highest-severity PRs from a 50-PR public benchmark, 147 bugs each proven by a failing test, one run per configuration. It was written by metareview's author, and the data and code are public. Treat it as evidence for a pilot, not proof about your repo.</p></div>
+  </div>
+  <p class="note">Source: <a href="https://dsifry.github.io/harnesseval/">HarnessEval, “Vibes vs. Evidence”</a> (September 2026). The full report has the confidence intervals and methods.</p>
+</section>

+<section class="slide" data-part="How it works">
+  <div class="eyebrow">Part 2 · How it works <em>· vocabulary</em></div>
+  <h2>Nine words you'll see everywhere</h2>
+  <dl class="gloss">
+    <div><dt>gate</dt><dd>A named review at a specific point, like <code>task-done</code> or <code>pr-ready</code>. It returns a verdict.</dd></div>
+    <div><dt>verdict</dt><dd>The gate's answer: <code>PASS</code>, <code>PASS_ADVISORY</code>, <code>NEEDS_REVISION</code> or <code>ESCALATED</code>.</dd></div>
+    <div><dt>finding</dt><dd>One specific issue. <strong>Blocking</strong> findings stop the gate; <strong>advisory</strong> and <strong>follow-up</strong> ones inform you but don't.</dd></div>
+    <div><dt>lens</dt><dd>One reviewer's point of view: security, testing quality, architecture… Several lenses read the same change.</dd></div>
+    <div><dt>judge</dt><dd>A separate AI model that checks each finding and throws out the false alarms before anything blocks you.</dd></div>
+    <div><dt>base ref</dt><dd>The branch or commit you're comparing against, usually <code>main</code>. The review covers <code>base..HEAD</code>.</dd></div>
+    <div><dt>evidence receipt</dt><dd>A JSON record of a command you ran (like your tests): exit code, time, output hash. Proof, not a claim.</dd></div>
+    <div><dt>run ID</dt><dd>Every review gets one, like <code>mrv-2026…-task-done-cart-…</code>. You pass it back when you retry.</dd></div>
+    <div><dt>marker</dt><dd>A small record saying “an AI lens review of <em>this exact diff</em> happened, and here's its verdict.”</dd></div>
+  </dl>
+</section>

+<section class="slide" data-part="How it works">
+  <div class="eyebrow">Part 2 · How it works <em>· the gates</em></div>
+  <h2>Gates are sized by how much work they look at</h2>
+  <div class="nest">
+    <div class="ring">
+      <div class="ring-h"><b>pr-ready</b><code>review pr-ready --base main</code></div>
+      <p class="ring-p">The whole branch, before you push or open a PR.</p>
+      <div class="ring">
+        <div class="ring-h"><b>epic-ready</b><code>review epic-ready &lt;epic&gt;</code></div>
+        <p class="ring-p">A bigger feature, once all its tasks are done: do the pieces work together and still match the original goal?</p>
+        <div class="ring core">
+          <div class="ring-h"><b>task-done</b><code>review task-done &lt;task&gt;</code></div>
+          <p class="ring-p">One small chunk of code. <strong>You'll run this one the most.</strong></p>
+        </div>
+      </div>
+    </div>
+    <div class="side-gates">
+      <div class="panel"><span class="tag">Before any code</span><h3>artifact</h3><p>Reviews a spec, plan, or design doc. <code>review artifact docs/plan.md</code></p></div>
+      <div class="panel"><span class="tag">After merge</span><h3>learn --post-merge</h3><p>Pulls lessons from a merged PR. <code>learn --post-merge 42 --base &lt;sha&gt;</code></p></div>
+      <p class="note"><strong>Rule of thumb:</strong> use the smallest gate that matches the decision you're making right now.</p>
+    </div>
+  </div>
+</section>

+<section class="slide" data-part="How it works">
+  <div class="eyebrow">Part 2 · How it works <em>· verdicts</em></div>
+  <h2>Every gate ends in one of four verdicts</h2>
+  <div class="vt">
+    <div><span><span class="chip pass">PASS</span></span><span class="what">Nothing is blocking.</span><span class="do">Move on.</span></div>
+    <div><span><span class="chip adv">PASS_ADVISORY</span></span><span class="what">Nothing blocking, but there are notes worth reading.</span><span class="do">Move on <strong>only if</strong> the blocking count is zero. Read the advisories; they're often future bugs.</span></div>
+    <div><span><span class="chip rev">NEEDS_REVISION</span></span><span class="what">At least one blocking finding.</span><span class="do">Fix it, then re-run the <strong>same</strong> gate with <code>--previous-run &lt;run-id&gt;</code>.</span></div>
+    <div><span><span class="chip esc">ESCALATED</span></span><span class="what">Retrying the same thing won't converge.</span><span class="do"><strong>Stop retrying.</strong> A human narrows, splits, or redesigns the work.</span></div>
+  </div>
+  <p class="note">Exit codes: <code>0</code> = passing verdict with zero blockers · <code>1</code> + a log path = open that log · non-zero with no path = read the error output. An artifact review starts as <span class="chip nr">NOT_REVIEWED</span>, which blocks until reviewers fill it in.</p>
+</section>
+
+<section class="slide" data-part="How it works">
+  <div class="eyebrow">Part 2 · How it works <em>· two halves</em></div>
+  <h2>A code gate needs two kinds of check to PASS</h2>
+  <div class="grid g2">
+    <div class="panel">
+      <span class="tag">Half 1 · no AI</span>
+      <h3>The structural check</h3>
+      <p>Fast and repeatable. It asks: is there a passing test receipt? Are earlier blockers resolved? Is the working tree clean? Is the mutation report clean? It can run in a git hook or in CI.</p>
+    </div>
+    <div class="panel">
+      <span class="tag">Half 2 · AI</span>
+      <h3>The adversarial lens review</h3>
+      <p>Several reviewer agents each read your diff through one lens and try to find problems. A judge model then confirms or rejects each finding. The result is saved as a <strong>marker</strong> for that exact diff.</p>
+    </div>
+  </div>
+  <div class="callout">Since 0.10, <code>task-done</code>, <code>epic-ready</code> and <code>pr-ready</code> won't PASS on the structural check alone. They need a recorded lens review of <strong>this exact <code>base..HEAD</code></strong>. Commit something new, or change the base, and you need a fresh review.</div>
+  <p class="note">Why the split? The structural half is cheap and can't be talked into anything. The AI half is where real bugs are found. Neither is enough alone.</p>
+</section>
+
+<section class="slide" data-part="How it works">
+  <div class="eyebrow">Part 2 · How it works <em>· lenses</em></div>
+  <h2>Ten lenses, each hunting for a different kind of problem</h2>
+  <div class="lens-list">
+    <div class="lens"><b>feasibility</b><span>Can this actually be built as described?</span></div>
+    <div class="lens"><b>completeness</b><span>Missing cases, steps, or requirements?</span></div>
+    <div class="lens"><b>scope</b><span>Does it stay on task, or wander?</span></div>
+    <div class="lens"><b>architecture</b><span>Fits the codebase's boundaries and patterns?</span></div>
+    <div class="lens"><b>intent</b><span>Still solves the original request?</span></div>
+    <div class="lens"><b>security</b><span>Injection, auth gaps, leaked secrets…</span></div>
+    <div class="lens"><b>testing-quality</b><span>Do tests actually prove the behavior?</span></div>
+    <div class="lens"><b>data-migration</b><span>Safe to change data and schemas?</span></div>
+    <div class="lens"><b>runtime-reliability</b><span>Unhandled async errors, retries, partial failure.</span></div>
+    <div class="lens"><b>mechanical-precision</b><span>Off-by-one, wrong names, exact details.</span></div>
+  </div>
+  <div class="grid g2">
+    <div class="plain"><h3>Findings must point at real lines (new in 0.12)</h3><p>Each finding names a file and line numbers in a fixed format. If it cites a file or line your diff never touched (±10 lines), it's rejected automatically. That catches invented findings.</p></div>
+    <div class="plain"><h3>Style nits are filtered out</h3><p>Advisory findings have to state a real consequence and hold up against the best counter-argument. Formatting nitpicks never reach you.</p></div>
+  </div>
+</section>
+
+<section class="slide" data-part="How it works">
+  <div class="eyebrow">Part 2 · How it works <em>· the fix loop</em></div>
+  <h2>The find-and-fix loop: <code style="font-size:.7em">metareview fsm</code></h2>
+  <div class="flow">
+    <div class="step"><small>discover</small><b>Review</b><p>Lens reviewers read the diff and propose findings.</p></div>
+    <div class="step"><small>adjudicate</small><b>Judge</b><p>A judge model confirms real bugs and drops false alarms.</p></div>
+    <div class="step"><small>fix</small><b>Fix</b><p>Your agent fixes the confirmed bugs and commits.</p></div>
+    <div class="step hi"><small>recheck</small><b>Re-review</b><p>A fresh review of the <em>fix</em>. Fixes often add bugs of their own.</p></div>
+    <div class="step"><small>done</small><b>Clean</b><p>Stops when a fresh review finds nothing, or at its iteration limit.</p></div>
+  </div>
+  <p class="loopback">recheck finds something → back to judge → fix → recheck</p>
+  <div class="grid g4">
+    <div class="plain"><h3><code>review-loop</code></h3><p>Review + judge only. No fixing.</p></div>
+    <div class="plain"><h3><code>sdlc-loop</code></h3><p>Review → judge → fix → verify.</p></div>
+    <div class="plain"><h3><code>sdlc-loop-clean</code></h3><p>Adds the re-review. <strong>Use this on your own diff.</strong></p></div>
+    <div class="plain"><h3><code>sdlc-loop-proved</code></h3><p>Each fix must come with proof, such as a test that fails before the fix and passes after.</p></div>
+  </div>
+  <p class="note">FSM stands for finite-state machine: the CLI decides which step comes next and records every step under <code>.metareview/runs/&lt;id&gt;/</code>. Your agent does the reviewing and fixing; the CLI runs the judge.</p>
+</section>

+  <div class="callout"><strong>Start at <code>--judge-effort low</code>.</strong> In HarnessEval, low effort was the fastest setting in 14 of 14 cases, and high effort showed no measurable gain over medium in 17 of 22 comparisons while usually costing more. Raise it only if your own results justify it.</div>
+  <p class="note">The judge used is recorded in each run's audit log. Using a <em>different</em> model family from the one that wrote the code is a good habit: it doesn't share the same blind spots. Never put a secret in <code>--var</code>; use the environment variables above.</p>
+</section>

+<section class="slide" data-part="How-tos" data-key="plan">
+  <div class="eyebrow">How-to <em>· review a plan before you build</em></div>
+  <h2>How to review a plan or spec before building it</h2>
+  <div class="recipe">
+    <div class="rstack">
+      <p class="when"><strong>When:</strong> you or your agent wrote a plan, spec, or design doc, and code is about to be written from it. Fixing a vague plan now is much cheaper than fixing vague code later.</p>
+      <ol class="steps">
+        <li><span><b>Save the plan as Markdown</b> in the repo, e.g. <code>docs/plans/cart-coupons.md</code>.</span></li>
+        <li><span><b>Ask your agent:</b> <code>/review-artifact docs/plans/cart-coupons.md</code></span></li>
+        <li><span>The agent creates a review log (it starts as <code>NOT_REVIEWED</code>), runs the <b>ten lenses as parallel subagents</b>, and fills in every reviewer row and the verdict.</span></li>
+        <li><span><b>Read the Blocking Findings</b> and revise the plan.</span></li>
+        <li><span><b>Re-review.</b> The retry links to the previous run with <code>--previous-run</code>.</span></li>
+      </ol>
+    </div>
+    <div class="rstack">
+      <div class="term"><div class="tb"><i></i><i></i><i></i><span>raw CLI</span></div>
+<pre><span class="p">$ </span>metareview review artifact docs/plans/cart-coupons.md
+<span class="c"># exits non-zero on purpose: the log is NOT_REVIEWED
+# until the ten lens reviewers fill it in</span>
+
+<span class="c"># after revising the plan:</span>
+<span class="p">$ </span>metareview review artifact docs/plans/cart-coupons.md \
+    --previous-run &lt;run-id&gt;</pre></div>
+      <div class="done"><span><code>PASS</code> or <code>PASS_ADVISORY</code> with zero blockers. Now start building.</span></div>
+      <p class="note">If a review was done without subagents, it must be labeled <code>in-session-emulated</code>. That's weaker evidence, and the log says so.</p>
+    </div>
+  </div>

+<section class="slide" data-part="How-tos" data-key="fix">
+  <div class="eyebrow">How-to <em>· review and fix your own diff</em></div>
+  <h2>How to find and fix bugs in your diff, before any gate</h2>
+  <div class="recipe">
+    <div class="rstack">
+      <p class="when"><strong>When:</strong> you've committed a chunk of work. This is the step that actually finds bugs. The gates then check that it happened.</p>
+      <ol class="steps">
+        <li><span><b>Commit your work.</b> The loop reviews committed <code>base..HEAD</code>, on a feature branch, never <code>main</code>.</span></li>
+        <li><span><b>Ask your agent:</b> <code>/fsm</code> run <code>sdlc-loop-clean</code> against <code>main</code>.</span></li>
+        <li><span>It loops <b>review → judge → fix → re-review</b>. Your agent reviews and fixes; the CLI runs the judge.</span></li>
+        <li><span><b><code>DONE</code></b> means a fresh review came back clean. <b><code>STOPPED</code></b> means it hit a limit; read what's left.</span></li>
+        <li><span><b>Read the fix commits</b> (<code>git log -p</code>) so you understand every change made for you.</span></li>
+        <li><span><b>Write down the run ID.</b> You'll need it to record the review for the gate.</span></li>

+<span class="p">$ </span>metareview fsm state      <span class="c"># lost? follow next_action</span>
+<span class="p">$ </span>metareview fsm advance    <span class="c"># exit 3 = your agent's turn</span>
+<span class="p">$ </span>metareview fsm record node-output --node discover --data findings.json
+<span class="p">$ </span>metareview fsm advance    <span class="c"># … repeat until DONE or STOPPED</span>
+<span class="p">$ </span>metareview fsm export --run &lt;run-id&gt;   <span class="c"># evidence bundle</span></pre></div>
+      <div class="scroll-x"><table class="et">
+        <thead><tr><th>fsm exit</th><th>Meaning</th><th>Do</th></tr></thead>
+        <tbody>
+          <tr><td>3</td><td>A step needs your agent</td><td>Do it, <code>record</code>, <code>advance</code></td></tr>
+          <tr><td>1 + GATE_FAILED</td><td>A check failed</td><td>Run the <code>resume_hint</code> (new run ID)</td></tr>

+  <div class="recipe">
+    <div class="rstack">
+      <p class="when"><strong>When:</strong> you believe one task-sized chunk is complete. <strong>Ask your agent:</strong> <code>/review-task-done docs/tasks/cart-total.md</code>. These are the steps it runs:</p>

+        <li><span><b>Commit everything.</b> Uncommitted changes aren't covered by the review.</span></li>

+<span class="c"># 5 · the gate</span>

+  <div class="eyebrow">How-to <em>· finish an epic</em></div>
+  <h2>How to finish an epic with epic-ready</h2>
+  <div class="recipe">
+    <div class="rstack">
+      <p class="when"><strong>When:</strong> a bigger feature was split into child tasks, and every child has passed task-done. epic-ready checks that the pieces work together and still match the original goal. <strong>Ask your agent:</strong> <code>/review-epic-ready docs/epics/coupons.md</code></p>
+      <ol class="steps">
+        <li><span><b>Commit everything.</b> A dirty tree blocks with <code>working-tree-unattested</code>.</span></li>
+        <li><span><b>Pick one base and reuse it:</b> the merge-base with main.</span></li>
+        <li><span><b>Run the epic review loop</b> over the combined diff. It uses the epic lenses: integration, intent, cross-task regressions, architecture.</span></li>
+        <li><span><b>Record it</b> with <code>--scope epic-ready</code> and the <b>same base</b>.</span></li>
+        <li><span><b>Run the gate</b>, then check the result still matches what the epic set out to do.</span></li>

+<span class="p">$ </span>metareview review record-lenses --scope epic-ready \
+    --base "$base" --verdict PASS --mode subagent-adjudicated \
+    --from-run &lt;fsm-run-id&gt; --lenses integration,intent
+<span class="p">$ </span>metareview review epic-ready docs/epics/coupons.md \
+    --base "$base" --evidence "$ev"</pre></div>
+      <div class="callout warn"><strong>Don't use <code>--base main</code> here.</strong> Once <code>main</code> moves forward, its tip no longer equals the merge-base, and your recorded review will never match. Use the same explicit <code>"$base"</code> in all three commands.</div>

+<section class="slide" data-part="When it says no" data-key="no">
+  <div class="eyebrow">Part 6 · When it says no <em>· the two “not yet” verdicts</em></div>
+  <h2>A “no” is information, not a failure</h2>
+  <div class="grid g2">
+    <div class="panel">
+      <span class="chip rev" style="align-self:flex-start">NEEDS_REVISION</span>
+      <h3>Fix, commit, re-run the same gate</h3>
+      <div class="term" style="margin-top:6px"><div class="tb"><i></i><i></i><i></i><span>retry</span></div>
+<pre><span class="p">$ </span>metareview review task-done docs/tasks/cart-total.md \
+    --base main --evidence "$ev" \
+    --previous-run mrv-20260922-…-cart-total-3f9a…</pre></div>
