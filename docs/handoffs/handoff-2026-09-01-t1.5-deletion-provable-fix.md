## 2. T1.5 scope (spec §9.4, §9.1, §9.6 — authoritative)

A `Kind:"deletion"` `DifferentialProof` carries a committed reproduction `Test` **and** a `DeletionRef`
(`proof.go:47-52`: `File, ParentSHA, FileBlob, Removed`). Proving it = **three** parts, all required:
- **(a) `DeletionRef`↔reviewed-diff binding (deterministic):** the fix commit's own diff
  (`FixEntryHead..Head`, per-file) must remove **exactly `Removed`** as `-` lines from `File`, anchored
  at the fix's parent. `Removed` is the deletion's identity; `FileBlob`+`ParentSHA` anchor the whole
  pre-deletion file in history (§9.4 lines 960-968). A free-floating or mismatched span is **malformed**.
- **(b) fail-before/pass-after reproduction:** the pre-fix tree still has the code → the `Test` fails
  (assertion); the post-fix tree removed it → the `Test` passes. **Reuse `Reproducer.Reproduce` AS-IS**
  (the deletion is materialized when `Head` is applied).
- **(c) whole-suite over-deletion scope check (NEW phase):** run the **full consent-hashed TestCmd
  (NO `-run` filter)** on **both** the pre-fix and post-fix worktrees. The baseline **must be green**
  (fail closed otherwise — a pre-existing red suite can't attribute blame); the post-deletion suite
  must **also be green**. A **green→red** transition means the deletion regressed an existing test →
  block. No per-test identity needed — a baseline-green/post-red delta is attributable to the deletion
  by construction (§9.4 honest-limits, ~26% over-deletion; §9.6).

**Outcome:** proven iff (a) binds ∧ (b) proven ∧ (c) green→green. Any failure → the honest bucket
(malformed for a bad `DeletionRef`; survived for a fix that doesn't hold / a green→red regression;
unverifiable for a red baseline or a tree that can't answer), mapped to the four `run.PinOutcome` values.

**Own-file / clause (a):** a deletion discharges clause (a) when `DeletionRef.File==Finding.File`
(§9.1). Enforce an own-file **bind** in the new `case run.ProofDeletion` (malformed if the deletion's
file isn't the finding's own file), analogous to the pin's `isAddedLineInFile` bind — this is the
deletion's own-file guarantee (distinct from §9.5's `Root.File` structural gate). A Proven deletion
then settles its finding via the existing `settled` map (`prove.go:200`), so clause (a) skips it.

**§9.2 reviewer:** a deletion's reproduction test should also be symptom-reviewed — broaden the guard
at `prove.go:188` to `Kind==reproduction || Kind==deletion`. `symptomVeto` already reads `Proof.Test`
+ `FailBefore`, both populated for a deletion, so no other wiring changes.

**Not in T1.5:** the §9.8 AST pre-screen is **T1.6**. §9.5's structural-class `Root.File` gate is separate.
