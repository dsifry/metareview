## 1. Scope (spec §9.6 — authoritative)

Deleting a **test** is a first-class reward-hack; a green suite afterward proves nothing. A test
deletion is legitimate iff **(A) mutation-kill non-regression holds** (always run — the deterministic
gate) **and (B) coverage non-regression holds wherever a per-line coverage profile is obtainable**
(absent — never a block — where §4.2's opaque cmd yields no profile). One predicate, not two: coverage
is a hard conjunct exactly when a signal exists. A test deleted because its code was deleted (paired,
one `DeletionRef`) is the legitimate case, proven safe by mutation-kill non-regression.

## 2. Hosting — DICTATED by the codebase: a NODE, not a gate

A `gate.Gate` gets only `(ctx, run.Snapshot, gate.Git)` — `gate.Git` is **read-only**
(`internal/fsm/gate/git.go:29-49`; no worktree-add, no exec) and a gate cannot obtain the fix diff,
the runner, or `gate.Exec`. Running tests/mutations across two trees needs process + worktree
execution, which **only a node gets** (`machine.ExecInput` carries `Diff`, `Runner`; the `prove` node
is the precedent). So build the §9.6 work as a **prove-style node / `Prover` method** that emits a
structural `run.Finding` (`Source: run.SourceMutationVerify`, blocking `Category`), and let the
existing **`pins_proven`** transition gate select on it — exactly the split already used for §9.4
(`ProveDeletions` does the work, `pins_proven` reads the finding). The "gate" in "test-deletion gate"
is the transition gate; the work is a node. **No new gate needed.** (Reference: `prove.go:51-57` the
`Prover` interface, `prove.go:35-42` `ProveSpec` with `PreFixSHA=FixEntryHead`/`PostFixSHA=Head`,
`cli/wiring.go:269` wiring, `internal/mutation/reproduction.go` the worktree engine.)

## 3. ⧗ DECISION #2 (MAINTAINER) — the killed-mutant SET source

§9.6(A) is "no mutant killed **before** the deletion survives **after** it." That needs a set of
already-killed mutants. **The codebase provides none, and does not dictate the answer:**
- The pin `Verifier` only verifies **agent-declared pins** handed to it — no corpus generator exists
  (grep-confirmed across `internal/mutation` + FSM).
- Proven pins are **NOT retained** as a typed list: the fold **clears** `Snapshot.Unproven` on a
  Proven result (`fold.go:160-163`) and keeps no "proven" list. The only durable trace is the raw
  prove-node `Delta` (`Pins`/`PinResults`) inside `Snapshot.NodeOutputs[nodekey]` as untyped
  `json.RawMessage` (`fold.go:117`; Delta at `types.go:185-187`).

**Two implementations, pick one (this is the decision):**

- **Option 1 — reuse the run's proven pin-kind `DifferentialProof`s as the mutant set** (RECOMMENDED;
  matches the spec's "reusing the pins' mutation engine"). Re-verify each previously-Proven pin on the
  **pre-deletion** tree (`FixEntryHead`) and the **post-deletion** tree (`Head`) with `Verifier`; a pin
  killed before that survives after → the deleted test was its detector → block. **Cost of Option 1:**
  the proven-pin set must be made available to the node. Sub-choice (also maintainer's): **(1a)** add a
  typed `Snapshot.Proven []DifferentialProof` maintained by the fold (mirrors `Unproven`; a wire-schema
  addition to a 100%-covered package), or **(1b)** a read-only typed accessor that recovers proven
  pins from `NodeOutputs` prove-deltas (no schema change; more code, keyed per node/iteration). 1a is
  cleaner and auditable; 1b avoids a schema change. **Recommend 1a.**
- **Option 2 — generate a fresh mutation corpus at node time** (NOT recommended). No generator exists;
  this is a whole net-new mutation-testing subsystem (mutant generation across files), expensive per
  fix (cf. `MaxPins=32`, `types.go:191`, which bounds pin cost deliberately), and goes well beyond
  "reuses the pins' engine."

**Why this is the maintainer's call:** Option 1a changes the persisted run wire schema; Option 2 is a
major new subsystem. Both are load-bearing and irreversible-ish. A builder must not guess.

## 4. ⧗ #1, #3, #4 — resolved here (recommendations; confirm in review)

- **#1 Mutant identity (`File+site+operator+span` + collision test).** Neither `run.PinID`
  (`types.go:239`, folds Finding+File+From+To — no line/operator) nor `report.Mutant`
  (`report.go:38-46`, has File/Line/Column/Operator but no id) matches. Add a small id function
  `mutantID(file, line, operator, span)` (operator = the From→To transform class; span = From) with a
  **collision test** (same mutated content at two sites, or two operators on one span, must get
  distinct ids) — the plan's named mutation-test. Lives in `internal/mutation` (floor pkg).
- **#3 Coverage-profile probe.** Net-new; no runtime coverage code exists. For a Go `go test` argv,
  append `-coverprofile=<tmp>` in a worktree run (reuse `Reproducer.suiteRun`/`runProc` DI), then check
  the file parses as a Go cover profile. The consent-hashed cmd is **opaque by contract** (so a profile
  is not guaranteed) → record **UNAVAILABLE, never a block** when absent (mirror `ScopeSuite` returning
  `PinUnverifiable` for a non-answering tree, `reproduction.go:301-322`). Coverage non-regression =
  whole-suite profile **before (test present) vs after (test deleted)**, diffed: a production line
  `covered→uncovered` (and not within a same-commit `DeletionRef.Removed`) → regression.
- **#4 Removed-test detection.** Deleted test **files** are free: `Reproducer.changedPartition`
  already buckets `part.delTests` (deleted `*_test.go`, `reproduction.go:130-139`). A removed test
  **function** in a surviving file needs a new predicate over `judge.RemovedLinesInFile(diff, path)`
  (`diffselect.go:246`) matching `^func (Test|Benchmark|Fuzz|Example)\w*\(` on removed (`-`) lines.
  Scan the node's `in.Diff.Text` (`FixEntryHead..Head`).

## 5. Deterministic-gate shape + exclusions

- A mutant whose **target span was removed in the same commit** — provable because it lies within a fix
  `DeletionRef.Removed` (§9.4) — is **EXCLUDED** from the non-regression set (its code is legitimately
  gone; not a lost kill). This is what lets a paired code+test deletion pass.
- Emit the finding via the established pattern (`SourceMutationVerify` + `CategoryUnprovenFix`) so
  `pins_proven` reddens; a survived-after-deletion mutant or a coverage `covered→uncovered` regression
  blocks. If coverage is unavailable, mutation-kill alone gates (recorded, not blocked).
- Acceptance (plan T2.1): a code+test paired deletion passes; a sole-detector test deletion reddens;
  the gate degrades to mutation-only under an opaque cmd.
